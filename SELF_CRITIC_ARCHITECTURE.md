# Self-Critic Architecture: Automated Falsification & Critique Protocols

Every improvement proposal generated by AlphaAlgo must undergo an automated **Self-Criticism Phase** where the proposing agent is forced to actively falsify its own hypothesis before submission.

---

## 1. Ten Critical Self-Criticism Questions

The Self-Critic Engine forces the proposing agent to provide machine-verifiable answers to the following ten diagnostic questions:

1. **What assumption could be wrong?**
   *   *Requirement*: Identify the key statistical, behavioral, or systemic assumption (e.g. constant correlation, infinite order book depth) that the hypothesis relies on.
2. **What evidence contradicts this?**
   *   *Requirement*: Retrieve the historical out-of-sample period (e.g., extreme regime shifts like Aug 2024 or Mar 2020) where the proposed mechanism would have regressed or triggered stop-losses.
3. **What simpler alternative exists?**
   *   *Requirement*: Explain why a simpler parameter tuning, static heuristic, or linear regression cannot achieve the same capability gain.
4. **What baseline could beat this?**
   *   *Requirement*: Compare the candidate against a standard buy-and-hold baseline, a simple Moving Average / Mean Reversion model, and the un-modified parent version.
5. **Could this improvement exploit the evaluator?**
   *   *Requirement*: Conduct an AST syntax scan over the code changes to confirm there are no modifications to dataset splits, metrics calculation, or mock score bypasses.
6. **Could this improvement create a new failure mode?**
   *   *Requirement*: Map the change to potential downstream failures, such as memory bloat, socket lockups, thread starvation, or API rate-limit exhaustion.
7. **Could this improvement increase complexity without increasing capability?**
   *   *Requirement*: Calculate the Cyclomatic Complexity delta and Lines of Code (LOC) delta. If LOC increases by $>15\%$ and capability gain is $<2\%$, flag as overengineered.
8. **Could the apparent improvement be caused by leakage?**
   *   *Requirement*: Run a data-leakage check to confirm that no out-of-sample data points (future prices, future volumes) were leaked into the feature engineering pipeline.
9. **Could the improvement only work in one market regime?**
   *   *Requirement*: Evaluate the candidate across at least three distinct regimes: High-Vol Bear, Low-Vol Bull, and Mean-Reverting Range.
10. **What evidence would falsify the proposal?**
    *   *Requirement*: Define the exact walk-forward out-of-sample performance threshold (e.g., Drawdown exceeding $5\%$ or Sharpe ratio dropping below baseline) that would cause immediate rejection.

---

## 2. Verification Protocol

If the proposer fails to provide sufficient evidence or answer any of these questions with clear mathematical and historical backtest data, the candidate's state is immediately set to `REJECTED` and it is banned from the `EvolutionGate` promotion queue.
This ensures that AlphaAlgo maintains a skeptical, falsification-based mindset rather than blindly accepting its own updates.
